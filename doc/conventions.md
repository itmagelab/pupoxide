# Соглашения по разработке

> Правила написания кода для этого проекта.
> Основано на [техническом видении](vision.md).

## Технологический стек

- **Язык**: Rust (последняя стабильная версия)
- **Runtime**: Tokio
- **База данных**: PostgreSQL (через SeaORM)
- **Архитектура**: Чистая архитектура / Модульный монолит

## Обязательные правила

### Стандарты разработки

- **ОБЯЗАТЕЛЬНО** следовать идиоматичному стилю Rust (используйте `cargo clippy`).
- **ОБЯЗАТЕЛЬНО** структурировать код логически по модулям в `src/`.
- **ЗАПРЕЩЕНО** использовать нестабильные (nightly) функции без веской причины.
- **ОБЯЗАТЕЛЬНО** использовать `Cargo.toml` для управления зависимостями и фичами.

### Безопасность кода

- **ЗАПРЕЩЕНО** использовать `unwrap()` и `expect()` (lint: `#![deny(clippy::unwrap_used)]`).
- **ОБЯЗАТЕЛЬНО** обрабатывать ошибки через `Result<T, E>`.
- **ОБЯЗАТЕЛЬНО** использовать `thiserror` для библиотечных ошибок и `anyhow` для прикладного уровня (application level).
- **ОБЯЗАТЕЛЬНО** использовать `?` оператор для пробрасывания ошибок.
- **ОБЯЗАТЕЛЬНО** логировать ошибки и важные события через `tracing`.

### Архитектурные принципы

- **Разделение ответственности**: Отделять логику работы с данными от бизнес-логики и транспортного уровня (API).
- **Dependency Injection**: Использовать внедрение зависимостей (через конструкторы или `State` в Axum) для облегчения тестирования.
- **Async по умолчанию**: Использовать `async/await` для всех I/O операций.

### Данные и Валидация

- **ОБЯЗАТЕЛЬНО** валидировать входные данные (рекомендуется crate `validator`).
- **ЗАПРЕЩЕНО** хранить секреты (пароли, ключи) в открытом виде или в коде. Используйте переменные окружения и `.env`.

## Именование

### Файлы и модули

- Все имена файлов и модулей в `snake_case`.
- Имена типов (struct, enum, trait) в `PascalCase`.
- Переменные и функции в `snake_case`.

## Тестирование

- **ОБЯЗАТЕЛЬНО** писать модульные тесты для бизнес-логики.
- **ОБЯЗАТЕЛЬНО** писать интеграционные тесты для API и работы с БД (в директории `tests/`).
- Использовать стандартный `cargo test`.

## Git

### Commit сообщения

- **ОБЯЗАТЕЛЬНО** использовать только английский язык.
- Формат: `<type>: <description>`
    - `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.
- Пример: `feat: implement user registration with password hashing`

## Работа с Git

- Спрашивать разрешение перед коммитом и пушем.
- Проверять код тестами и clippy перед коммитом.
