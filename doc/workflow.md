# Процесс разработки

> Инструкция для кодового ассистента по выполнению работ согласно [техническому видению](vision.md) и [плану задач](tasklist.md)

## Основные принципы

### Строгое следование плану

- Работа только по итерациям из [tasklist.md](tasklist.md).
- Выполнение задач в указанном порядке.
- Обязательное тестирование каждой итерации.
- **Каждые 10 завершённых итераций файл [tasklist.md](tasklist.md) переносится в архив, а новый tasklist.md создаётся пустым.**

## Алгоритм работы

### 1. Анализ текущей итерации

- [ ] Определить следующую незавершенную итерацию из tasklist.md.
- [ ] Изучить цель и список задач.
- [ ] Проанализировать существующий код.

### 2. Согласование решения

- [ ] **ОБЯЗАТЕЛЬНО**: Предложить архитектурное решение (Чистая архитектура / Модульный монолит) с описанием изменений.
- [ ] Показать изменения в модулях (domain, infrastructure, api/cli).

### 3. Реализация

- [ ] **ПОСЛЕДОВАТЕЛЬНО** выполнить каждую подзадачу.
- [ ] Следовать [соглашениям по разработке](conventions.md).
- [ ] Реализовывать логику в соответствующих слоях (Domain для логики, Infrastructure для БД/IO).
- [ ] Использовать SeaORM для работы с данными, если это предусмотрено архитектурой.

### 4. Тестирование

- [ ] Запустить `cargo test`.
- [ ] Проверить специфичные тест-кейсы итерации (модульные и интеграционные).
- [ ] Убедиться в корректности работы CLI/API.

### 5. Обновление прогресса

- [ ] Отметить выполненные задачи в tasklist.md.
- [ ] **ОЖИДАТЬ ПОДТВЕРЖДЕНИЯ** перед переходом к следующей итерации.

## Обязательные проверки

### Перед завершением итерации

- ✅ Код соответствует [conventions.md](conventions.md).
- ✅ Отсутствие `unwrap`/`expect` в прикладном коде.
- ✅ Пройден `cargo clippy`.

### Архитектурные требования

- ✅ Соблюдение границ слоев (Domain не зависит от Infrastructure).
- ✅ Обработка ошибок через `Result` и crate `anyhow`/`thiserror`.

## Запрещенные действия

### ❌ НЕЛЬЗЯ

- Начинать кодирование без согласования архитектуры.
- Писать "сырой" SQL без необходимости (использовать SeaORM или SQLx Query Builder).

## Коммуникация

### Согласование решения

```markdown
## Итерация X: [Название]

### Предлагаемое решение:
[Описание подхода и изменений в модулях]

### План изменений:
- [ ] Создать структуру данных `...` в `src/domain/...`
- [ ] Реализовать логику в `src/infrastructure/...`
- [ ] Добавить интеграционный тест в `tests/...`

Согласны с таким подходом?
```
