# Инструкции и Правила для Gemini (Pupoxide)

Этот файл автоматически считывается моделями Gemini и средой Antigravity IDE при инициализации проекта. Всегда строго следуй указанным ниже правилам, архитектурным ограничениям и конвенциям разработки проекта Pupoxide. Более подробные детали и контекст смотрите в [основном файле конвенций (doc/conventions.md)](doc/conventions.md).

---

## 1. Общие правила общения и поведения

*   **Философия ресурсов**: Мы создаем только базовые ресурсы (File, Directory, Exec), из которых уже используя RHAI мы делаем более сложные, например package или service и любые другие.
*   **Язык общения**: Все обсуждения, объяснения и комментарии в чате с пользователем ведутся **исключительно на русском языке**.
*   **Автоматическое создание документов**: **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** автоматически создавать новые файлы документации или другие документы без явного, прямого запроса пользователя.
*   **Git коммиты**:
    *   Язык сообщений коммитов — **английский**.
    *   Формат коммитов: `type: description` (например, `feat: add postgres connection pool`).
    *   **ОБЯЗАТЕЛЬНО** запрашивать разрешение у пользователя перед выполнением команды `git push`.

## 2. Технологический стек проекта

*   **Язык**: Rust (Latest Stable).
*   **Async Runtime**: `tokio`.
*   **Web Server (Master API)**: `axum`.
*   **HTTP Client (Agent Client)**: `reqwest`.
*   **TLS/mTLS**: `tokio-rustls` (для безопасной коммуникации Agent-Master).
*   **Сертификаты**: `rcgen` (генерация и подпись CSR).
*   **База данных**: PostgreSQL + `sea-orm` + `sea-query`.
*   **Обработка ошибок**: `anyhow` (единообразно по всему проекту).
*   **Логирование/Трассировка**: `tracing` + `tracing-subscriber`.
*   **Сериализация**: `serde` + `serde_json` / `serde_yaml`.
*   **Валидация данных**: `validator`.

## 3. Архитектура: Модульный монолит (Hexagonal / Ports & Adapters)

Код проекта разделен на четыре логических слоя внутри `src/`:

1.  **Domain (`src/domain/`)**: Чистая бизнес-логика и Ports (трейты). Сущности (entities), правила валидации. Не имеет внешних зависимостей.
2.  **Infrastructure (`src/infrastructure/`)**: Adapters. Реализация ввода-вывода (взаимодействие с БД через SeaORM, системные CLI-вызовы, работа с файловой системой). Зависит от Domain.
3.  **Application (`src/application/`)**: Use Cases. Координирует потоки данных между Domain и Infrastructure.
4.  **Interface (`src/interface/`)**: CLI (`clap`) и другие точки входа.

### Строгие правила слоев (Layer Purity):
*   **Domain Purity (Чистота Домена)**:
    *   Внутри слоя `domain` **ЗАПРЕЩЕНО** зависеть от любых внешних библиотек, кроме `serde`, `thiserror` и `validator`.
    *   **ЗАПРЕЩЕНО** использовать типы из слоев Infrastructure или Application внутри Domain.
    *   Все внешние интерфейсы (база данных, API, системные утилиты) должны быть описаны в Domain в виде абстрактных интерфейсов — `trait` (Ports).
*   **База данных и SeaORM**:
    *   Сущности SeaORM (`Entity`) и файлы миграций физически находятся исключительно в слое `src/infrastructure/`.
    *   Слой Domain не должен ничего знать о SeaORM или конкретной базе данных. Конвертация между моделями БД (SeaORM) и доменными моделями происходит в слое Infrastructure.
*   **Данные и Сериализация**:
    *   Используй `serde` для моделей данных, передаваемых между слоями.
    *   Валидация входных данных должна происходить на уровне Domain с помощью библиотеки `validator`.

## 4. Кодовые стандарты Rust

*   **Форматирование и Линтер**:
    *   Обязательно использование `cargo fmt` и `cargo clippy`.
    *   В кодовой базе обязательно должен присутствовать архитектурный линт `#![deny(clippy::unwrap_used)]`.
    *   **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** отключать или подавлять любые предупреждения компилятора или линтера (через `#[allow(...)]` или подобные атрибуты). Все предупреждения компилятора и линтера Clippy должны исправляться в соответствии с текущей версией компилятора.
*   **Безопасность типов**:
    *   **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** использовать `unwrap()` и `expect()` внутри директории `src/`.
    *   *Исключение*: Unit-тесты и редкие явные инварианты, которые должны сопровождаться подробным документирующим комментарием, объясняющим безопасность операции.
*   **Обработка ошибок (Error Handling)**:
    *   Везде в проекте для единообразия возвращай тип `anyhow::Result<T>` (т.е. `Result<T, anyhow::Error>`).
    *   Создавай новые ошибки с помощью макроса `anyhow::anyhow!()` для добавления понятных контекстных сообщений.
    *   Используй `.context()` и `.with_context()` для обогащения ошибок контекстом при их распространении вверх по стеку вызовов.
*   **Логирование (Logging)**:
    *   Используй макросы `tracing::info!`, `tracing::warn!`, `tracing::error!`, `tracing::debug!`.
    *   Всегда добавляй структурный контекст к логам через поля, например: `tracing::info!(resource_id = %id, "Processing resource")`.

## 5. Тестирование

*   **Разработка через тестирование (TDD)**: В проекте используется подход TDD (Test-Driven Development). Разработка любой новой функциональности или исправление ошибок начинается с написания теста (модульного или интеграционного), проверяющего требуемое поведение или воспроизводящего проблему. Реализация пишется только после того, как тест создан и запущен (изначально падает).
*   **Unit-тесты**: Обязательны для проверки логики домена. Пишутся в тех же файлах, где находится тестируемый код (внутри блоков `mod tests`).
*   **Интеграционные тесты**: Располагаются в директории `tests/` и проверяют сквозные сценарии: `Interface -> Application -> Infrastructure` (с реальной или тестовой БД).
